# PRD: 기획 문서 협업 서비스

## 1. 제품 개요

### 제품명

가칭 `mdhub`

### 한 줄 소개

프로젝트 단위로 에픽, 태스크, 마크다운 문서를 관리하고, 각 업무와 문서를
서로 연결할 수 있는 팀 협업용 기획 서비스

### 문제 정의

기획 업무는 에픽, 태스크, 문서가 서로 연결되어 있어야 맥락이 살아난다.
하지만 실제로는 다음 문제가 자주 발생한다.

- 태스크와 관련 문서가 분리되어 있다
- 문서끼리 관계를 관리하기 어렵다
- 프로젝트별 기획 산출물이 흩어져 있다
- 최신 문서와 관련 업무를 한 화면에서 파악하기 어렵다

### 목표

- 프로젝트 단위로 기획 업무를 구조화한다
- 에픽과 태스크를 생성하고 관리할 수 있다
- 마크다운 문서를 웹에서 작성하고 관리할 수 있다
- 태스크와 문서를 연결할 수 있다
- 문서와 문서를 연결할 수 있다
- 팀 단위 협업에서 참여자 기준으로 접근 범위를 통제한다

## 2. 타겟 사용자

- PM / PO

- 디자이너
- 개발자
- 작은 팀 단위 협업 조직

## 4. 핵심 기능

### 4-1. 로그인 및 진입

사용자는 GitHub 또는 Google 계정으로 로그인할 수 있어야 한다.

세부 내용:

- 소셜 로그인 지원
- 최초 로그인 시 사용자 프로필 생성
- 로그인 후 내가 생성했거나 내가 속한 프로젝트 목록으로 진입

### 4-2. 프로젝트 생성 및 참여

사용자는 프로젝트를 생성할 수 있고, 협업 단위로 프로젝트에 참여할 수 있어야
한다.

세부 내용:

- 프로젝트 생성
- 프로젝트 이름, 설명 입력
- 팀 협업용 프로젝트 운영
- 사용자는 프로젝트에 반드시 소속되어야 한다
- 프로젝트 목록에는 내가 생성한 프로젝트와 내가 속한 프로젝트가 모두 표시된다
- 프로젝트 생성 플로우는 2단계로 구성한다

2단계 생성 플로우 예시:

1. 기본 정보 입력: 프로젝트 이름, 설명
2. 참여/구조 설정: 초기 참여자 또는 기본 운영 정보 확인

### 4-3. 에픽 생성

사용자는 프로젝트 내에서 에픽을 생성하고 관리할 수 있어야 한다.

세부 내용:

- 에픽 생성
- 제목, 설명, 상태 입력
- 프로젝트 단위 목록 조회
- 에픽 상세 조회

### 4-4. 태스크 생성

사용자는 프로젝트 내에서 태스크를 생성하고, 특정 에픽에 소속시킬 수 있어야
한다.

세부 내용:

- 태스크 생성
- 제목, 설명, 상태 입력
- 에픽 선택
- 태스크 목록 및 상세 조회
- 상태는 `backlog`, `todo`, `in progress`, `done` 네 단계만 사용한다

### 4-5. 마크다운 문서 생성

사용자는 프로젝트 내에서 마크다운 문서를 작성하고 저장할 수 있어야 한다.

세부 내용:

- 문서 생성
- 제목 입력
- 마크다운 본문 작성
- 문서 저장 및 수정
- 문서 목록 및 상세 조회
- 편집 화면은 스플릿 뷰를 사용한다
- 좌측에서 마크다운 작성, 우측에서 즉시 프리뷰를 제공한다
- 자동 저장은 지원하지 않는다
- 제목은 필수값이며 내용은 선택값이다

### 4-6. 태스크와 문서 연결

사용자는 특정 태스크에 관련 문서를 연결할 수 있어야 한다.

세부 내용:

- 태스크 상세에서 관련 문서 추가
- 하나의 태스크에 여러 문서 연결 가능
- 연결된 문서 목록 조회
- 연결 해제 가능

### 4-7. 문서와 문서 연결

사용자는 문서 상세에서 관련 문서를 연결할 수 있어야 한다.

세부 내용:

- 문서 상세에서 관련 문서 검색 및 연결
- 하나의 문서에 여러 관련 문서 연결 가능
- 연결된 관련 문서 목록 조회
- 연결 해제 가능

### 4-8. 검색 범위 제한

검색은 프로젝트 내부 데이터로만 제한해야 한다.

세부 내용:

- 프로젝트 안에서만 검색 허용
- 다른 프로젝트의 문서, 태스크, 에픽은 검색 결과에 노출하지 않는다
- 연결 대상 검색도 현재 프로젝트 범위 내에서만 가능하다

## 5. 핵심 유저 스토리

- 사용자는 GitHub 또는 Google 계정으로 로그인할 수 있어야 한다
- 사용자는 새 프로젝트를 생성할 수 있어야 한다
- 사용자는 내가 생성했거나 내가 속한 프로젝트 목록을 볼 수 있어야 한다
- 사용자는 프로젝트 내에서 에픽을 생성할 수 있어야 한다
- 사용자는 에픽 하위에 태스크를 생성할 수 있어야 한다
- 사용자는 프로젝트 내에서 마크다운 문서를 생성할 수 있어야 한다
- 사용자는 태스크에서 관련 문서를 연결할 수 있어야 한다
- 사용자는 문서에서 관련 문서를 연결할 수 있어야 한다
- 사용자는 프로젝트 내부에서만 문서/업무를 검색할 수 있어야 한다

## 7. 성공 기준

- 사용자가 로그인 후 프로젝트를 생성할 수 있다
- 사용자가 내가 생성했거나 내가 속한 프로젝트에 접근할 수 있다
- 프로젝트 안에서 에픽, 태스크, 문서를 각각 생성할 수 있다
- 태스크에 문서를 연결할 수 있다
- 문서에 다른 문서를 연결할 수 있다
- 연결된 관계가 상세 화면에서 정상적으로 조회된다
- 검색 결과가 현재 프로젝트 범위 내로 제한된다

## 8. 제품 구조 원칙

- 프로젝트는 최상위 작업 단위다
- 에픽과 태스크는 프로젝트에 속한다
- 문서는 프로젝트에 속한다
- 사용자는 접근하려는 프로젝트에 반드시 속해야 한다
- 태스크와 문서는 다대다 관계로 연결된다
- 문서와 문서는 자기참조 관계로 연결된다
- 핵심 데이터는 모두 DB에 저장한다
- 검색 및 연결 가능 범위는 현재 프로젝트 내부로 제한한다

## 9. 운영 정책

### 9-1. 삭제 정책

MVP에서는 주요 객체의 삭제 기능을 제한한다.

- 프로젝트 삭제는 금지한다
- 문서 완전 삭제는 금지한다
- 관계 해제 시 원본 객체는 삭제하지 않는다
- 연결 해제는 연결 관계만 끊는다
- 관계가 해제된 상태는 화면에서 식별 가능하게 표시한다

### 9-2. 삭제 정책 상세 설명

삭제를 금지하는 이유는 협업 맥락 보존 때문이다. 프로젝트와 문서는 여러
업무와 연결될 수 있으므로, 단순 삭제를 허용하면 참조 무결성과 작업 이력이
쉽게 깨진다. 따라서 MVP에서는 "원본 삭제"보다 "연결 관계 해제"를 기본 정책으로
삼는다.

이 정책에 따라 사용자가 태스크-문서 또는 문서-문서 관계를 해제하더라도 실제
문서나 태스크 본문은 유지된다. 사용자는 현재 화면에서 관계가 제거되었는지 여부를
확인할 수 있어야 하며, 이후 복구 가능성까지 고려해 객체 자체 삭제보다 안전한
운영 방식을 우선 적용한다.
