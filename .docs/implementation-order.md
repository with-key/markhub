# 기능 구현 순서 문서

## 1. 문서 목적

본 문서는 `.docs/prd.md`와 기능별 명세서를 기준으로 MVP 기능을 어떤 순서로
구현해야 하는지 정리한 문서다. 구현 순서는 기능 간 의존관계, 검증 난이도,
사용자 흐름 완성도를 기준으로 결정한다.

## 2. 구현 순서 원칙

- 먼저 구현하는 기능은 뒤 기능의 선행조건이어야 한다.
- 프로젝트 컨텍스트와 접근 제어가 잡히기 전에는 도메인 기능을 확장하지 않는다.
- 연결 기능은 원본 객체 생성과 조회가 먼저 가능해야 구현한다.
- 검색은 대상 데이터와 권한 제한 규칙이 안정화된 뒤 구현한다.

## 3. 권장 구현 순서

### 1단계. 인증 및 사용자 진입 구조

대상 기능:

- 로그인 및 진입

선행 이유:

- 이후 모든 기능은 로그인 사용자와 세션 정보가 있어야 동작한다.
- 프로젝트 목록, 생성, 멤버십 검사 모두 사용자 식별이 선행되어야 한다.

완료 기준:

- GitHub 로그인 가능
- Google 로그인 가능
- 최초 로그인 시 프로필 생성 가능
- 로그인 후 프로젝트 목록 화면 진입 가능

참조 문서:

- `.docs/features/auth-login/spec.md`
- `.docs/features/auth-login/policy.md`
- `.docs/common/policy.md`

### 2단계. 프로젝트 컨텍스트 구축

대상 기능:

- 프로젝트 생성 및 프로젝트 목록

선행 이유:

- 에픽, 태스크, 문서, 검색은 모두 프로젝트 단위로 동작한다.
- 프로젝트 소속 개념이 먼저 있어야 데이터 범위 제한과 접근 제어를 구현할 수 있다.

완료 기준:

- 프로젝트 2단계 생성 플로우 동작
- 생성자 자동 멤버 등록
- 내가 생성했거나 참여 중인 프로젝트 목록 조회 가능
- 멤버가 아닌 프로젝트 접근 차단 가능

참조 문서:

- `.docs/features/projects/spec.md`
- `.docs/features/projects/policy.md`
- `.docs/common/policy.md`

### 3단계. 기본 도메인 객체 생성

대상 기능:

- 에픽 생성 및 조회
- 태스크 생성 및 조회
- 마크다운 문서 생성, 수정, 조회

선행 이유:

- 연결 기능은 태스크와 문서가 먼저 존재해야 한다.
- 검색 기능도 검색 대상 데이터가 먼저 구축되어야 검증 가능하다.
- 사용자가 실제 업무 데이터를 만들 수 있어야 MVP의 핵심 가치가 드러난다.

권장 내부 순서:

1. 에픽
2. 태스크
3. 문서

내부 순서 이유:

- 태스크는 에픽 선택 기능이 있으므로 에픽이 먼저 구현되는 편이 자연스럽다.
- 문서는 연결과 검색의 핵심 대상이므로 생성/수정/상세까지 안정적으로 만든 뒤
  관계 기능으로 넘어가는 것이 좋다.

완료 기준:

- 프로젝트 단위 에픽 목록/상세 가능
- 프로젝트 단위 태스크 목록/상세 가능
- 태스크 생성 시 에픽 선택 가능
- 문서 생성/수정/상세/목록 가능
- 문서 편집 화면 스플릿 뷰 동작

참조 문서:

- `.docs/features/epics/spec.md`
- `.docs/features/tasks/spec.md`
- `.docs/features/documents/spec.md`
- 각 기능별 `policy.md`

### 4단계. 관계 기능 구현

대상 기능:

- 태스크-문서 연결
- 문서-문서 연결

선행 이유:

- 관계 기능은 태스크와 문서의 생성, 조회, 상세 화면이 준비되어 있어야 붙일 수 있다.
- 검색 범위 제한 규칙도 연결 대상 선택 UI에서 함께 검증할 수 있다.

권장 내부 순서:

1. 태스크-문서 연결
2. 문서-문서 연결

내부 순서 이유:

- 태스크-문서 연결은 핵심 사용자 가치가 더 직접적이다.
- 문서-문서 연결은 같은 방식의 검색 및 연결 패턴을 재사용할 수 있다.

완료 기준:

- 태스크 상세에서 문서 연결/해제 가능
- 문서 상세에서 관련 문서 연결/해제 가능
- 중복 연결 방지 가능
- 동일 프로젝트 범위 내 대상만 연결 가능

참조 문서:

- `.docs/features/task-document-links/spec.md`
- `.docs/features/document-document-links/spec.md`
- 각 기능별 `policy.md`
- `.docs/common/policy.md`

### 5단계. 프로젝트 내부 검색

대상 기능:

- 검색 범위 제한

선행 이유:

- 검색은 에픽, 태스크, 문서 데이터가 모두 준비된 후에 구현해야 검증 범위가 명확하다.
- 연결 기능에서 사용할 검색 UI와 공통 규칙을 마지막에 정리하기 좋다.

완료 기준:

- 현재 프로젝트 범위의 에픽, 태스크, 문서 검색 가능
- 다른 프로젝트 데이터 미노출 보장
- 연결 대상 검색에도 동일한 범위 제한 적용
- 빈 결과 및 권한 없음 처리 가능

참조 문서:

- `.docs/features/search/spec.md`
- `.docs/features/search/policy.md`
- `.docs/common/policy.md`

## 4. 실무 권장 작업 단위

### 배치 A. 인프라 및 접근 제어

- 인증 연동
- 사용자 프로필 생성
- 프로젝트 멤버십 검사 공통 처리
- 프로젝트 컨텍스트 라우팅

### 배치 B. 프로젝트 및 기본 CRUD

- 프로젝트 생성/목록
- 에픽 생성/목록/상세
- 태스크 생성/목록/상세
- 문서 생성/수정/목록/상세

### 배치 C. 관계 및 검색

- 태스크-문서 연결
- 문서-문서 연결
- 프로젝트 내부 검색

## 5. 권장 검증 순서

1. 로그인 후 프로젝트 목록까지 진입되는지 확인한다.
2. 프로젝트 생성 후 해당 프로젝트에 접근 가능한지 확인한다.
3. 프로젝트 내에서 에픽, 태스크, 문서를 각각 생성할 수 있는지 확인한다.
4. 태스크 상세에서 문서를 연결하고 해제할 수 있는지 확인한다.
5. 문서 상세에서 관련 문서를 연결하고 해제할 수 있는지 확인한다.
6. 검색 결과가 현재 프로젝트 범위 내로만 제한되는지 확인한다.

## 6. 최종 권장 구현 순서 요약

1. 로그인 및 진입
2. 프로젝트 생성 및 프로젝트 목록
3. 에픽 생성 및 조회
4. 태스크 생성 및 조회
5. 문서 생성, 수정, 조회
6. 태스크-문서 연결
7. 문서-문서 연결
8. 프로젝트 내부 검색
